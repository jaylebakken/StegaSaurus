## Outcome

Build two deliberately separate services:

1. **Registry service:** a concise, authenticated system of record for songs,
   recipient-specific exports, retained private attribution records, and
   registry-only lineage. The Saurus desktop app remains the first encode and
   verification client.
2. **Public-web discovery service:** a policy-aware crawler that searches
   permitted public sources for likely copies of registered client songs. It
   creates reviewable song-match candidates; it does not independently accuse
   a recipient or prove that a copy leaked.

The systems meet only through narrow identifiers and queues. The crawler must
not receive watermark keys, private carrier maps, recipient labels, notes, or
general registry search access.

## Current Starting Point

- The guided desktop app encodes a four-byte handle and writes a local
  `*.saurus.json` sidecar containing business labels and the retained private
  block record.
- Desktop decode verifies one user-selected retained claim. It does not discover
  an unknown handle.
- The V4 workflow supports known-song localization and export-record fanout in
  memory. Its current fingerprint is a clean-file localizer, not an open-web or
  platform-transcode fingerprint.
- Registry-only lineage is the supported product direction: generate each
  export from the clean master and store ancestry in the registry. Do not stack
  independent child watermarks.
- The measured 15-second robust profile covers only the named repository
  baseline. It is not evidence of general codec, platform, microphone, or
  adversarial robustness.
- `MASTER_SECRET` is currently embedded in desktop source. That is suitable only
  for a local prototype and must not become the production key model.

## Product Boundaries

### Registry MVP Includes

- Tenant-scoped songs and exports.
- Server-issued, collision-checked audio handles.
- Versioned retained attribution records.
- Registry-only parent and child lineage.
- Desktop authentication, idempotent create/finalize operations, and audit logs.
- Explicit export states: `reserved`, `active`, `failed`, `revoked`.
- Claimed-record retrieval for an authorized desktop verification workflow.

### Registry MVP Excludes

- Blind or global handle discovery.
- Stacked watermark lineage.
- Server-side audio processing.
- Public registry lookup.
- Legal conclusions about fault or responsibility.
- Claims of robustness beyond named measured evaluations.

### Discovery MVP Includes

- Client-approved monitoring targets and sources.
- Search/API connectors plus polite crawling of permitted public pages.
- Metadata-first collection and bounded media-preview acquisition.
- Song-level candidate matching with confidence and provenance.
- Human review, suppression, retry, and takedown/opt-out workflows.

### Discovery MVP Excludes

- Authentication bypass, paywall circumvention, CAPTCHA evasion, or stealth
  scraping.
- Private groups, direct messages, cloud drives, or customer accounts.
- Automatic recipient attribution.
- Automatic legal notices or public accusations.
- A promise of complete web coverage.

## Proposed Architecture

```text
Saurus desktop
  | HTTPS + device/user token
  v
Registry API ---- Registry database
  |                    |
  |                    +-- encrypted attribution records
  |                    +-- append-only audit events
  +---- object store references, only if later required

Client monitoring catalog (song IDs + public matching material only)
  |
  v
Discovery scheduler -> source connectors -> isolated media worker
  |                                           |
  +---- discovery database <--- matcher <------+
                  |
                  v
            review queue / alerts
                  |
            explicit authorized handoff
                  v
       desktop or future verification worker
```

Deploy the registry and discovery service as separate processes, databases,
credentials, and network roles. A shared repository is acceptable initially;
a shared trust boundary is not.

## Track A: Concise Registry Service

### Recommended First Shape

Use a small HTTP API with PostgreSQL in deployment and SQLite for isolated local
development. Keep the transport framework behind application services so the
audio package remains independent from HTTP and storage. Schema migrations are
mandatory from the first persistent version.

Suggested modules:

```text
src/saurus_registry/
  api/            # HTTP routes and request/response schemas
  application/    # reserve, finalize, resolve, revoke, lineage
  domain/         # immutable records and policy
  storage/        # repository interfaces and SQL implementation
  security/       # auth context, record encryption, audit helpers
```

### Minimal Data Model

| Record | Required fields |
| --- | --- |
| Tenant | `tenant_id`, name, status, created timestamp |
| Device/user | subject ID, tenant ID, role, credential metadata, status |
| Song | internal UUID, tenant ID, title, client reference, source digest, audio geometry, fingerprint version |
| Export | internal UUID, song ID, four-byte audio handle, recipient label, parent export ID, state, timestamps |
| Attribution record | export ID, codec/profile version, encrypted serialized block record, record digest |
| Registry event | event ID, actor, action, object IDs, timestamp, request ID, before/after digests |

Recipient labels and notes are user-supplied context. A verification result may
say that audio matched a system-created export event; it must not state that the
named person caused a leak.

The four-byte audio handle is not a safe global primary key. Use a UUID as the
database identity, enforce uniqueness at least within a song and tenant, detect
collisions transactionally, and measure collision pressure. Changing payload
width requires a separate codec/version decision.

### Minimal API

| Method | Route | Purpose |
| --- | --- | --- |
| `POST` | `/v1/songs` | Register source identity and geometry |
| `GET` | `/v1/songs/{song_id}` | Read an authorized song record |
| `POST` | `/v1/songs/{song_id}/exports:reserve` | Reserve export ID and random audio handle |
| `POST` | `/v1/exports/{export_id}:finalize` | Store record after local encode and clean verification |
| `POST` | `/v1/exports/{export_id}:fail` | Close an unusable reservation with diagnostics |
| `GET` | `/v1/exports/{export_id}` | Read labels, state, and lineage pointers |
| `GET` | `/v1/exports/{export_id}/verification-record` | Retrieve the private record with strict authorization and audit |
| `POST` | `/v1/exports/{export_id}:revoke` | Revoke future operational use without deleting history |
| `GET` | `/v1/exports/{export_id}/lineage` | Read registry ancestry |

Mutating requests require an idempotency key. Responses carry schema version,
request ID, and server timestamp. Errors must distinguish validation,
authorization, conflict, expired reservation, and retryable service failure.

### Desktop Encode Transaction

1. User selects the clean source and enters project and recipient context.
2. Desktop authenticates and creates or selects a song.
3. Desktop reserves an export; the server atomically issues an unused handle.
4. Desktop encodes locally from the clean source with that exact handle.
5. Desktop runs the current clean self-verification gate.
6. On success, desktop finalizes the export with the versioned retained record,
   output digest, geometry, and profile. On failure it marks the reservation
   failed and may request another handle.
7. Desktop writes a small recovery receipt containing server URL, tenant ID,
   song ID, export ID, record digest, and no recipient secrets.

Never mark an export active before the encoded artifact passes the local gate
and the retained record is durably committed. Preserve the clean master; child
exports are always regenerated from it.

### Desktop Verification Transaction

1. User selects suspicious audio and a receipt/export, or first selects a known
   registered song for authorized fanout.
2. Desktop requests only the required record or bounded song export bundle.
3. Desktop verifies locally and reports accepted, rejected, or abstained with
   diagnostics.
4. Desktop posts a concise verification event without uploading audio by
   default.
5. UI wording distinguishes audio evidence, registry facts, and user labels.

Introduce a `RegistryBackend` boundary in `saurus_app`; implement local-sidecar
and remote backends during migration. Keep codec calls in the existing audio
boundary and HTTP calls out of `stegosaurus.audio`.

### Registry Security Baseline

- TLS only; no secrets or tokens in URLs or logs.
- Short-lived user/device access tokens stored in the OS credential store.
- Tenant and role checks in application services, not only route decorators.
- Envelope encryption for retained attribution records and sensitive labels.
- Separate registry authentication, watermark derivation, and data-encryption
  keys with rotation metadata.
- Append-only audit records for record access and every state change.
- Request limits, pagination, bounded fanout, and anomaly alerts.
- Backups with tested restore, retention, deletion, and tenant export procedures.
- No hardcoded shared production watermark secret in the desktop binary.

## Track B: Public-Web Discovery Service

### Discovery Pipeline

```text
approved target songs
  -> source-specific search/API queries
  -> public page candidates
  -> metadata and canonical URL normalization
  -> policy/robots/allowlist decision
  -> bounded permitted media or preview fetch
  -> isolated decode and normalization
  -> robust song fingerprint match
  -> deduplication and confidence policy
  -> human review queue
  -> optional explicit attribution verification handoff
```

Use official APIs, feeds, and search providers before general crawling. Each
connector owns its source policy, rate limit, retry behavior, URL rules, and
data-retention rule. Identify the crawler honestly and provide an operational
contact and opt-out path.

The existing log-band localization fingerprint is not suitable for open-web
song recognition. Evaluate a proven audio-fingerprinting engine or licensed
recognition API against a held-out corpus containing codecs, excerpts, edits,
and negative controls before selecting it. Keep song recognition and Saurus
recipient attribution as separate evidence stages.

### Candidate Record

Store only what is necessary for review and replay:

- Candidate ID, tenant ID, and registry song ID.
- Source connector, canonical public URL, discovery timestamp, and page title.
- Public author/account label as unverified page context.
- Matching engine/version, score, matched duration, and decision threshold.
- Fetch policy result, content digest, and minimal retained evidence reference.
- Review state, reviewer, suppression reason, and expiry timestamp.

Do not copy recipient labels or private attribution records into this database.
Default to hashes, features, and short permitted evidence rather than retaining
full media. Define retention with counsel and client agreements before launch.

### Crawler Safety Baseline

- Allowlisted schemes and destinations; block loopback, link-local, private,
  cloud-metadata, and redirect-to-private addresses to prevent SSRF.
- Sandboxed media decoding with CPU, memory, duration, byte, redirect, archive,
  and timeout limits.
- MIME inspection and content sniffing; never trust filename extensions.
- Per-host concurrency and request budgets, exponential backoff, and kill switch.
- Robots and source terms review recorded per connector.
- No browser credential reuse and no execution of downloaded files.
- Malware scanning and quarantine for retained artifacts.
- Signed job inputs and least-privilege worker credentials.
- Manual review before any attribution workflow, client alert escalation, or
  external action.

## Principal Pitfalls And Gates

| Pitfall or shortcoming | Consequence | Required mitigation or gate |
| --- | --- | --- |
| Four-byte handle collisions | Ambiguous or failed export issuance at scale | Transactional collision checks, UUID identities, per-song scoping, capacity metric, payload-width review |
| Shared desktop secret | One extracted binary can compromise every tenant | Replace hardcoded secret; define per-tenant/per-device derivation and rotation before production |
| Partial reserve/finalize failure | Orphaned handles or registry entries without usable audio | Idempotency, state machine, expiry, retry queue, reconciliation job |
| Record format drift | Old exports become unverifiable | Versioned canonical serialization, migration policy, golden fixtures |
| Registry compromise | Private recipient context and verification material exposed | Encryption, least privilege, audit, incident response, external security review |
| User labels treated as proof | Unfair or legally risky accusations | Separate system facts from labels in schema, API, UI, and reports |
| Open-world false song matches | Irrelevant or damaging alerts | Held-out negatives, calibrated thresholds, human review, explicit uncertainty |
| Short platform previews | Song may match but carry too little watermark evidence | Report `song candidate only`; never infer recipient attribution |
| Platform transforms | Current localizer or watermark may fail | Connector-specific evaluation; abstain when the measured envelope is exceeded |
| Crawler coverage gaps | Missed public copies and false confidence | Publish coverage metrics and source status; never promise exhaustive search |
| Terms, robots, copyright, privacy | Blocking, liability, or trust damage | Source review, counsel, data minimization, retention and opt-out policy |
| Hostile pages or media | SSRF, parser exploit, resource exhaustion | Network isolation, sandboxed decoding, strict limits, patch cadence |
| Duplicate/reposted content | Alert fatigue and distorted metrics | Canonical URLs, content hashes, clustering, suppression controls |
| Tenant cross-contamination | Data leak or incorrect attribution | Tenant-scoped repositories, authorization tests, separate discovery projection |
| Verification fanout growth | Slow desktop checks and record overexposure | Known-song prefilter, bounded bundles, pagination, later server-side jobs |
| Offline desktop use | Failed workflows during registry outage | Explicit pending queue and recovery receipts; never silently activate locally |
